# Telegram attachments change contract

Baseline: fork danpysmak/todoist_bot master 81253e9. Feature branch only; never change live bot or merge. Preserve help/about/logout and per-user OAuth.

Approved scope: native Todoist-hosted file uploads and attachment comments; title from text/caption or safe filename/type fallback. Support largest photo, document, audio, voice, video/video note, animation, all sticker formats as files. Albums share one task by chat/media_group_id, each incoming item one comment; late captions retained in comments (no brittle debounce). Unsupported content and failed/oversized attachments receive explicit messages, never false success. Durable SQLite task/upload/comment stage checkpointing keyed by bot identity + chat/message (album key for shared task), serialize same-key work, stable Todoist request UUIDs, bounded safe retry. Do not silently lose files on webhook async acknowledgment: synchronous processing for attachment workflow or durable inbox required.

Security: optional multi-user compatibility but production personal mode requires explicit OWNER_TELEGRAM_ID; private chat plus actual sender enforcement before DB/OAuth/tasks. Verify OAuth state exactly before exchanging code; strong random state, consume after authorization; no raw interaction/token/error-body logging. Telegram download URL stays server side; fixed HTTPS host, no redirects, validated relative paths, strict size cap (default 5 MB for Todoist free-plan compatibility; max Telegram cloud 20 MB). Sanitize filename/header injection while preserving Unicode. Partial success retains task and retries missing stage, not duplicate task. Upload orphan window documented.

Official sources inspected: https://core.telegram.org/bots/api#getfile (curl official HTML: 20 MB cloud download; token-bearing private URL; one-hour minimum URL validity); https://developer.todoist.com/api/v1/ (POST /api/v1/uploads multipart file or binary with Content-Type/X-File-Name returns file_url,file_name,file_type,resource_type; POST /api/v1/comments requires content plus task_id and attachment object). OAuth scope data:read_write needed for comments/uploads, existing task:add users must reauthorize. Don't equate mock tests with live proof.

Deployment: fix Docker to build runnable release, preserve injected environment (existing rel/env.sh.eex empties ALL secrets); PORT fallback; optional/disabled Discord logging by default; persistent SQLite /data volume, health endpoint. Railway runbook includes BotFather, OAuth redirect /authorization/finish, webhook vs polling, exact vars, single instance, no overlap on same bot token, backups/WAL and rollback, smoke paths. CI tests/format/production release and Docker when viable.

No live deployment authorized absent credentials/project ownership/cost approval. Elixir installed for actual local tests/build. Document these as real gates; no purchases or production mutation.
